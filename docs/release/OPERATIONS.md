# خطة تشغيل وتراجع واستعادة — لا تنفذ إنتاجاً من هذا الملف

## قبل تشغيل الإنتاج

- اسم قاعدة/schema/role لا يثبت الانفصال: تحقق من current_database وserver
  identity بمصدر مستقل، وقارن مع هوية التطوير المثبتة دون عرض connection URL.
- المالك الإداري للمخطط مختلف عن دور التطبيق. NOSUPERUSER وNOBYPASSRLS،
  يلزم تسجيل الدخول بدور التطبيق نفسه، لا اتصال إداري يتخفّى عبر SET ROLE:
  غلاف التشغيل يشترط current_user=session_user واسم login مطابقاً للدور.
  ودور التطبيق ليس مالك الجداول. امنح الاستخدام والقراءة/الكتابة المحددة فقط؛
  لا GRANT ALL، ولا صلاحية DDL أو تعديل الموافقات/الموازنات للمخطط.
- افحص RLS على goals/plans/work_queue/executions/verifications/world_facts
  بدور التطبيق نفسه، وبأمثلة كيان مسموح/ممنوع وغياب tenant context.
  اختبر بقية جداول البيانات والـpolicies قبل منحها، لا يكتفي launch preflight
  الذي يفحص الحد الأدنى هذا.
- افصل أسرار الإنتاج عن SESSION_SECRET للتطوير. CC وMCP برمزين مستقلين؛
  hosts/origins دقيقة دون wildcard وTLS خارجي. MCP غير مطلوب ومغلق افتراضياً.
- OAuth: إثبات grant للاتصال المحدد لا metadata «authorized» وحدها،
  والاتصال واسع grant مخاطرة موثقة حتى لو GET فقط عملياً. لا scopes جديدة،
  لا توسعة resource allowlist، لا Gmail send ولا Drive write. الغلاف الحالي
  لا يمرر أسرار OAuth/نموذج إطلاقاً، وليس إثبات OAuth إنتاج.

## الترحيلات

الترحيلات العشرة الأصلية ثابتة وتستخدم سجل hashes وقفل advisory وtransactions.
**لا migration في start:release أو startup/build hook**.

- لقواعد Replit المُدارة: معاينة فرق schema عبر Publish ومراجعته وفق مسار
  المنصة، وفحص التوافق/RLS بعده. لا تشغيل db:migrate يدوياً على production
  بديلاً عن مسار النشر المُدار.
- لقاعدة خارجية قائمة: احتفظ بالمزود، وافصل دور migration عن دور التطبيق،
  واستخدم خطوة ترحيل مضبوطة مستقلة مع نسخة احتياطية وتحقق hashes/ACL.
- لا نقل بيانات التطوير الاصطناعية أو receipts أو جلسات تفويضها إلى الإنتاج.
- هذه المرحلة لم تنشئ هدف إنتاج أو دوراً إنتاجياً ولم تعدل migration أصلية.

## Backup + restore قبل الإطلاق

حدد RPO/RTO والاحتفاظ والتشفير ومكان النسخة بعد قرار المالك؛ لا تُفترض أرقام.
استخدم النسخ/point-in-time restore التي يتيحها مزود القاعدة مع توثيق وقت النسخة.
أي export منطقي يُنشأ عبر قناة آمنة دون credentials في command line/logs.

اختبار الاستعادة يكون إلى قاعدة أخرى محجوبة الشبكة، لا overwrite للقاعدة النشطة:
1. إثبات هوية قاعدة الاستعادة وانفصالها.
2. استعادة schema/البيانات/ACL/sequence ضمن ضوابط المزود.
3. مطابقة schema hash وRLS/least privilege، وعينات hashes دون عرض المحتوى.
4. **عدم تشغيل العامل أو outbox أو OAuth أو النماذج على النسخة المستعادة**:
   صفوف queue/claims القديمة قد تعيد أعمالاً مدفوعة أو خارجية إن فُعّلت.
5. توثيق الزمن والحجم وRPO/RTO الملاحظين؛ حذف النسخة فقط بقرار مالك مناسب.

لا يوجد restore إنتاج مثبت في هذه المرحلة.

## المراقبة

- `/livez` حياة العملية فقط. `/readyz` استعداد العامل والـDB، لا نجاح الأهداف.
- `/_sam/status` مصادق: عمليات/إعادات تشغيل، ticks/errors/dependencyFailures
  والوقت وحالة inFlight. لا معرفات tenant ولا requests ولا نص provider.
- native supervisor وCommand Center يعرضان queue/health/incidents في نطاق RLS؛
  لا تعتبر null أو excluded metrics صفراً.
- الغلاف يمنع modelAdapters والقدرات side-effect وغير المعتمدة. cost budget=0
  سياسة منع، recordedCost=null غياب قياس لا إعلان مجانية.
- قبل تفعيل inference: ledger مربوط بهدف/tenant وprices رسمية غير صفرية،
  سقف حجز قبل الشبكة، receipts token، منع retry غير معتمد، تنبيه اقتراب السقف.
  aggregate غير معزول لـmodel_calls لا يكفي لإثبات كلفة كيان معين.
- أنشئ سياسة تنبيهات لانعدام ticks/lease stale/queue age/DB outage/مزود
  مرفوض/نفاد retries/كلفة. قناة التنبيه وأرقام العتبات تحتاج إعداد إنتاج واعتماداً؛
  لم يُربط إرسال خارجي في هذه المرحلة.

## الانقطاع أثناء ACT

غلاف الإصدار يضبط `SAM_WORK_LEASE_MAX_ATTEMPTS=3` افتراضياً (نطاق 1–20).
الإعداد اختياري خارج الغلاف؛ عدم وجوده يحافظ على سلوك سام الأصلي.
عند نفاد المحاولات يصبح العمل FAILED وينتقل الهدف إلى FAILED إن سمح عقد
حالاته، داخل معاملة مقفلة وبـfencing صالح؛ لا تمديد غير محدود ولا استدعاء
نموذج لإخفاء الفشل. الاستدعاء المتعارض أو token القديم لا يغيّر الهدف.
هذا حد لمحاولات العمل، منفصل عن حد إعادة تشغيل العملية وعن ميزانية النموذج.

لا يمكن الادعاء بـexactly-once لكل أثر خارجي. نافذة الاختبار المثبتة محلية:
أثر idempotent محفوظ ثم قتل العامل قبل سجل التنفيذ. إعادة التفويض بعد انتهاء
lease تعيد الأثر نفسه، وترفض fencing token السابق ثم تتحقق باستقلال.
إغلاق المعاينة ليس توقف العامل؛ توقف بيئة التطوير أو العملية/الحاوية أمر آخر.

SIGTERM يخفض readiness ويوقف tick جديد وينتظر الجاري؛ انتهاء grace قد ينتج
SIGKILL ثم الاستعادة بعد lease expiry. لا تمدد lease أو تعاود أثر خارجي دون
عقد idempotency/reconciliation واضح. إخفاق المزود لا يعيد طلباً مدفوعاً هنا.

## Rollback

1. اعزل الإدخال الجديد، readiness غير جاهز، أوقف العامل بإيقاف آمن.
2. راجع الأعمال الجارية وfencing/leases/outbox؛ لا تصفرها ولا حذف receipts.
3. ارجع إلى commit منشور سابق متوافق مع schema، عبر إجراء نشر جديد معتمد،
   لا force-push ولا rewrite history.
4. code rollback ليس DB restore. إذا تغيّر schema لا تنفذ down migration
   تخريبية تلقائياً؛ استعادة منفصلة مع تقييم الأعمال التي وقعت منذ نقطة الاستعادة.
5. إعادة تشغيل بعد تحقق RLS والنسخة والمراقبة؛ لا تشغيل نسختين فعالتين على
   queue نفسها إلا إذا ثبت lease/fencing والـinstance identities.

لا تنفيذ لهذه الخطوات على الإنتاج ضمن هذا التكليف.
