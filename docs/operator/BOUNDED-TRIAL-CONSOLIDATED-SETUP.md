## Recommended minimum-impact topology

Use the **same existing Render runtime service and the same existing PostgreSQL database**, with a dedicated synthetic application schema (proposed name `sam_eval_once`, subject to owner-approved collision checks). This is an isolated namespace, not another database, host, project, workspace or service. Keep operational tables and serving roles unchanged. Deploy only the existing runtime temporarily; leave the existing MCP service on its operational connection and release.

Why a separate schema: 00108 installs invoker-rights triggers on every plan/execution insert in its schema. Both query evaluation_trials even for ordinary goals. Installing them on operational tables without additional SELECT privileges can break ordinary writers. Making them work there would require additional operational-role privileges/policies or reviewed guard changes. The shared profile also replaces a function. An isolated schema keeps those consequences off operational tables; merely calling the migrations “additive” would conceal their effect.

This option duplicates the candidate's dependent core/integration tables in one empty schema, rather than pretending seven feature tables are standalone. It minimizes changes to operational authority, not total table count. Existing isolated acceptance uses per-schema databases and actual scoped LOGINs, but no claim is made that this exact managed-database setup has been rehearsed.

Use a verified, unused, ordinary non-owner LOGIN if the operator finds one satisfying every check below. The three named application/database roles cannot be assumed unused: do not repurpose sam_runtime_app or sam_mcp_app, and do not run as the database owner. A NOLOGIN role plus SET ROLE is not a substitute: admission requires current_user=session_user and forbids memberships. If no eligible existing LOGIN exists, one narrowly scoped LOGIN (proposed `sam_eval_once_app`) and its operator-managed credential are genuinely required by this design. That is an explicit security setup decision, not authority possessed by this child or a new hosting requirement.

## Trusted owner approval: what is and is not already supported

Current code accepts an exact **Ed25519** signed SAM_LIVE_EVALUATION_APPROVAL, verified against a separately trusted public key. SAM MCP's existing owner authentication is RS256 OAuth/login; its tokens and key are not trial signatures, and Render browser login is not an Ed25519 trust anchor. Existing approvals rows, environment “approved” flags, fixture keys and the coding agent's assertion cannot satisfy the gate. Do not reuse/export an OAuth signing private key or treat fixture signatures as owner consent.

Minimal current-code proposal: an authorized operator verifies and reuses an existing organizational Ed25519 signer if one actually exists, otherwise establishes **one operator-custodied signing mechanism** under explicit owner approval. The setup must identify custodian, key generation/storage boundary, public-key fingerprint/provenance, who can request a signature, rotation/revocation and audit receipt. No separate application/server is required; no private key belongs in the SAM runtime. Owner approves the exact manifest and ceilings through the trusted operator process, which signs only that approved payload. Runtime receives the public key and scoped signed JSON through the existing service's authorized file/secret delivery mechanism, with exact paths and file readability checked. That delivery mechanism is not yet verified and is part of the same setup package. The child does not create keys or sign as owner.

A future authenticated SAM-owner approval endpoint could avoid introducing a separate signer ceremony, but there is **no such evaluated bridge today**. It would change the authorization contract and need reviewed code, anti-replay/custody semantics and exact acceptance before use. It is not the minimum current-code proposal and cannot be substituted by weakening authorizeLiveEvaluation. No bypass is recommended.

The signed payload must exactly bind kind, trialId, rootGoalId, companyId, specHash, final release commit R, corpusHash, endpoint, prices and exact expiresAt. specHash binds three child IDs, capabilityHash, limits and agent budgets. The public key's provenance must be established independently of the supplied signature file. Seal/export trace signing must likewise use an approved attested evidence signer; fixture signing material is not an owner trust root.
