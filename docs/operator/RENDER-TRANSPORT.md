# Concrete Render operator transport (disabled live composition)

`apps/agents/src/evaluation/renderTransport.ts` implements Render HTTP calls and durable recovery for the existing launcher. This is executable transport code, not the former interface-only proposal. It does not provision PostgreSQL, establish owner authority, enable the live interlock or read ambient credentials.

## Binding

An operator module calls `createRenderLaunchAdministration(options, trialAdministration)` and returns its `admin`, the existing owner-controlled `signer`, and `close: () => admin.close()` to `scripts/evaluation/launch.ts`. Options explicitly bind the service ID/allowlist, workspace ID, immutable LaunchRequest, prepared Render build ID, exact trial environment overrides, a private local state directory and a lazy `credential(signal)` callback. The callback must obtain the already approved API credential from operator custody; no environment-variable/token-file fallback exists. The SQL trial administration supplies the existing trial create/lookup/capture/observe route, confirms stopped workers, and independently verifies runtime commit/trial readiness. No model or runtime capability can select these bindings.

Use one stable private directory per operation and the unchanged launcher journal for recovery. The transport independently holds the existing persistent kernel lock on its private directory. Call `close()` after operations finish; it rejects while a method is running. The private fsynced snapshot contains service-local configuration, including connection/secret values needed for exact restoration: directory 0700, files 0600, atomic rename and directory fsync. Store it on the operator's encrypted local storage; never publish it. Public launcher journals contain only its opaque scope reference. A changed request, service, build, endpoint or override set cannot reuse it.

The production API origin is fixed at https://api.render.com/v1/. The only alternate origin is explicitly fixture-mode HTTP on 127.0.0.1; it cannot be selected for live mode. Redirects are rejected, and errors omit tokens, response bodies and configuration. HTTP uses the provided abort signal combined with lock-lease cancellation. This module does not generate any credential or signing key.

## Actual operations

1. Read service identity and require matching allowlist/workspace and autodeploy off. Snapshot the single live release, direct env/secret-file values, relevant service configuration and linked environment-group metadata. Individual GET endpoints distinguish direct values from inherited values; restoration deletes trial overrides that were originally absent. Group link/update metadata is checked for drift, never modified. The snapshot refuses existing files with the two reserved trial filenames.
2. POST suspend, read back suspended state, require zero instances and the independent stopped-worker check. Never infer quiescence from a successful HTTP status alone.
3. PUT individual `sam-eval-owner-public.pem` and `sam-eval-approval.json` secret files; PUT individual approved environment settings and actual trial/commit/path settings. No bulk replacements or environment-group writes. Each write records intent durably first and verifies the resulting value afterward.
4. POST `/deploys` with the exact prepared `buildId`, reconcile the deploy receipt/commit and terminal status while suspended, then POST resume and independently verify the running commit/trial. No build-from-branch fallback, latest-commit fallback or blind restart.
5. Recovery reconciles any pending operation before suspension/restoration. It restores only the recorded changed cells, preserves unrelated configuration, rolls back to the original deploy when needed, resumes and verifies the original release/configuration. The two added approval files are individually deleted. Drift or an unresolved operation remains explicitly pending, not 'restored'. Runtime-role revocation and signing/API-key custody revocation remain with the separate approved database/custodian procedures.

Mutations are never automatically retried after response loss. A lost cell response requires matching readback; an absent result cannot establish that a delayed write will never arrive. A lost deployment response requires one unambiguous new receipt against the pre-request baseline, the expected commit and terminal status. Multiple receipts, redirects, unreadable state, changed configuration or unresolved cancellation stop progress. Documented definite HTTP rejections clear the intent without implying success; subsequent restoration can undo earlier completed changes. An operator must correct a rejected restoration action before invoking recovery again. A crash after intent but before actual dispatch is intentionally indistinguishable from a lost request: recovery does not invent non-execution or resend it.

## Tests and scope of proof

`tests/isolated/render_transport.ts` uses an actual loopback HTTP server and the existing launcher, not mocked helper return values. It covers normal completion of the orchestration (deliberately blocked goal), partial delivery rejection, response loss for a file/deploy, unknown delayed application, cancellation, real SIGKILL after server-side deploy application, failed restoration followed by recovery, changed configuration, inherited-setting restoration, linked-group drift, wrong service/origin, redirects, ambiguous receipts and concurrent private-state access. A public RFC 8032 test vector supplies fixture-only signatures; it is not generated credential material and must never be trusted in production. No hosted API, provider, production database or owner signer is contacted.

The test is included in the existing isolated full-acceptance stage. Focused evidence must identify its exact application commit separately from earlier full-suite checkpoints. Sanitized traces can be exported with SAM_RENDER_TRANSPORT_EVIDENCE_DIR; private snapshots and credential-bearing bodies are excluded.

## Genuine hosted acceptance limits

Render's documented endpoints establish available operations, but not an atomic configuration/deployment transaction, compare-and-swap, an idempotency key, or guaranteed restart duration. This transport requires an exclusive operator maintenance window and rechecks drift; it cannot prevent an unrelated administrator from racing a change after readback. It detects linked-group changes through their API metadata, not cryptographic attestation of effective process environment. Hosted verification must validate the final effective configuration and original credential identity through the approved operator route without disclosing values.

The safety-preserving sequence specifically requires the existing service to accept application of a prepared build/rollback while suspended and to preserve that selected release when resumed. Official references reviewed do not establish that lifecycle behavior for this actual service. The simulator tests both acceptance and rejection; rejection fails closed and restores the original running configuration without starting evaluation. **Do not treat the successful simulation as proof that Render supports this sequence.** If actual documented/platform behavior rejects it, an alternate approved in-service dispatch pause/fenced activation design is needed before paid execution. There is no resume-old-worker-first fallback in this code.

Actual hosted acceptance must additionally establish prepared-build identity, new-file materialization, zero old instances/leases, effective settings/credential restoration, approval-file removal from the replacement process, and timing within the unchanged five-minute trial deadline. Cleanup retains the launcher's bounded windows; a slow remote deployment leaves restoration pending for scoped recovery. No gate or deadline was changed to make these tests pass.
